Verdict

Do not expand the current feature set yet. The reported spawn failures come from a concrete timing bug, not vague server instability. Safezone code also changes native process-wide protection settings and can leave a player invulnerable after leaving SCP-914.

  • Port the lifecycle cleanup already explored on local branch codex/bot-architecture-refactor-20260823. Take the focused fixes, not the whole branch.
  • Rewrite the bot population controller around one owned reconciliation loop. Count live, initialized bots, not dictionary entries.
  • Rewrite safezone enforcement around LabAPI events and native zone bounds. Remove godmode and all writes to SpawnProtected statics.
  • Move role changes and item grants behind server-authoritative policy. Spectator, zone, reconnect, and stale SSS state must never expand player authority or reset cooldowns.
  • Create StatsBots as a new companion. Leave StatsSystem, CustomizableUIMeow, PlayerBadge, and AdditionalNameTags unchanged.
  • Use HSM for player text and ServerKeybinds for SSS. Keep bot and nav diagnostics admin-only.
  • Do not patch a shared upstream plugin in place. Fork it from a pinned commit, keep the upstream directory untouched, and deploy either the compatible fork or upstream, never both.

Dependency rule

SCPSLBot, WarmupSafezone, and the new StatsBots product are in scope. Existing metarepo dependencies are not. If a required API is missing, create a fork in a new directory, record its upstream commit in the fork README, keep existing public behavior compatible, and put all new behavior behind tests.

A process-wide owner needs special handling. The planned ServerKeybinds fork must remain a drop-in ServerKeybinds.dll so existing consumers bind to one registry. The package must never contain both the upstream build and the fork build.

Stats, tags, HSM, and SSS

Build StatsBots, not another database

StatsBots should use the existing StatsSystem provider and its default player_stats store. Add reserved keys such as Warmup.BotKills, Warmup.BotDeaths, Warmup.Score, Warmup.BestStreak, Warmup.TagUnlocked.<id>, and Warmup.SelectedTagCode.

Keep the default store because StatsSystem hydrates it on join. Its extra stores do not have a public per-player hydrate method. Do not copy or edit StatsSystem storage code.

Only authenticated real users may write warmup keys. A managed bot must be identified through a tiny public SCPSLBot contract, not Player.IsDummy and never ID_Dummy.

Stop fighting over player names and badges

Do not write Player.DisplayName, the native badge, or group state. AdditionalNameTags and PlayerBadge already own those paths. That ownership conflict is the likely source of the wonky tag behavior seen in deployed companions.

Render the selected warmup title inside the StatsBots HSM profile card. Persist grants and selection through namespaced StatsSystem keys. Admin commands should use an exact full UserId for offline players and reject ambiguous nicknames.

If a safe tag API cannot replace only the StatsBots-owned entry, omit the native tag. Losing one cosmetic line is better than overwriting a staff badge.

SSS execution rules

ControlServer rule
All action dropdownsOpening or acquiring SSS never performs an action. ServerKeybinds records the first value for each per-player send generation as the baseline. Only a later, deliberate value change executes. Refresh after success so the menu reflects current state.
Respawn asBuild options per player from the same RoleEligibilityService used by execution. Show exact roles that can be assigned now. Do not show a generic SCP option. Omit unavailable roles completely. If no alternative is valid, omit the dropdown and show a short read-only explanation.
Regular role authorityDo not show Respawn as to a spectator. A regular player physically on Surface, or using a preset that disallows SCP players, receives no SCP options. Becoming Spectator, dying, reconnecting, or changing zones never expands role authority. Resolve the source state and facility zone from the server when the request arrives.
Stale role choiceRecheck eligibility when the value arrives. If the role became unavailable after the menu was sent, reject it, send a short native RA broadcast, and refresh SSS. Never fall back to Chaos, Class-D, or another role.
Role placementResolve and validate the destination anchor before changing role. An SCP role always uses the preset's allowed SCP spawn anchor and never inherits a spectator or Surface position. Verify the actual role after SetRole; cancellation or mismatch is a failed request, not permission to substitute another role.
Admin force roleUse a separate Tools control with an exact permission check. It may bypass regular zone, spectator, and role-cap rules. Its explicit allowlist includes RoleTypeId.Tutorial. Selecting Tutorial calls the native role change with RoleChangeReason.RemoteAdmin and verifies that the resulting role is Tutorial.
Global arena controlsVisibility and execution require either the configured RA permission or exactly one connected non-dummy player. Managed bots and test dummies do not count. A second real player immediately removes the block from non-admins and invalidates stale callbacks. When the server returns to one real player, refresh the remaining player and restore the block.
Population transitionJoin and leave events request a refresh only when they change a player's visible control set. The active arena preset stays in force when permission changes. Only control ownership changes.
Titles and togglesTitle selection saves immediately and lists only unlocked titles. Two-button display settings remain ordinary on/off choices and do not respawn or teleport anyone.
Interest managementEvery state event first resolves an affected-player set. A personal action, role or zone change, permission change, title change, or cooldown expiry invalidates only that player. Population boundaries invalidate only the players whose global-control visibility changed. Never rebuild or resend every player's SSS because one player's model changed.
Refresh triggersRequest a per-player refresh only after a join send, warmup enable or disable, a one-player to two-player boundary change, permission change, role eligibility fingerprint change, title grant or revoke, successful action that changes visible options, or that player's next item cooldown expiry. Do not poll SSS and do not refresh it for live stats or countdown text.
Refresh budgetRoute every request through one coordinator. Debounce for 500 ms, coalesce all pending reasons, require at least two seconds between sends to the same player, and cap at six sends per player in any rolling 60 seconds. A newer request replaces the queued snapshot instead of adding another send.
Change fingerprintHash the final per-player categories, setting IDs, labels, options, defaults, hints, language, and visibility. If the hash matches the last sent view, suppress the send. Security policy changes take effect immediately even when the visible menu is waiting for its rate-limited refresh.
Population fan-outA transition from one to two real players refreshes the former sole player and sends the normal join view to the newcomer. Two to three and larger changes do not refresh existing players because global-control visibility is already admin-only. A transition from two to one refreshes only the remaining player. Even a server-wide mode or config change becomes a set of independent per-player invalidations and sends only changed fingerprints.
DiagnosticsExpose per-player last-send time and fingerprint plus process counters for requested, sent, coalesced, rate-limited, and identical-snapshot refreshes. Log only abnormal sustained suppression, not every skipped request.

The current ServerKeybinds dropdown API stores one fixed option array. Exact per-player role visibility needs an addition such as AddDropdownForPlayer(Func<Player, DropdownModel>), plus acquisition-baseline tracking, an interest index, and a per-player refresh coordinator. Add them only in a new compatibility-fork directory. Do not edit the upstream ServerKeybinds project. Keep the merge, interest routing, fingerprint, and rate limit inside the fork rather than registering settings directly from StatsBots. Personalized state must never call a global block-changed or refresh-all path.

Concrete fix plan

This is the order I would use. Each step has a hard acceptance test. Do not start the next feature phase until the current gate passes.

Remove unconditional PostBuild deployment from the test and reload projects. Move both out of the release solution. Add a semantic version and a permission-gated bot_status command with mode, desired count, tracked count, live count, readiness, nav generation, last reconcile, last spawn error, AI runner health, and parked faults.

Done when: Release build writes only under bin, has zero warnings, and bot_status explains every spawn refusal.

Fix bot lifecycle and spawning

Done when: 20 cold boots and 20 round restarts reach exactly three live bots within 12 seconds. Three injected spawn failures recover. Mid-round reload recovers without a round restart.
